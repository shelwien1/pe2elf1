MPEG-1 / MPEG-2 audio · bitstream reference

Layer II vs Layer III

Two frame formats from the same standard, built on the same 32-band filterbank, carrying the same number of samples in the same number of bytes — and almost nothing else in common. This is the field-by-field comparison behind mp2.cpp, which repacks Layer II subband samples into a Layer III container. Every width here was checked against the decoder in mp3_A.h.

Byte figures throughout are the real numbers from frame 0 of Creditsmix_Comp.mp2 (160 kbit/s, 44.1 kHz, joint stereo, bound = 4, 27 subbands), next to a Layer III frame at the same bitrate and sample rate.

01  /  frame anatomy

What a frame is made of

Both stacks below are one 522-byte frame carrying 1152 samples per channel. Layer II spends 20 % of the frame describing how the samples are quantized and 78 % on the samples themselves, all inline, in that order. Layer III moves every parameter into a fixed-size side info block and lets the payload spill across frame boundaries.

Everything a decoder needs is in the frame, in stream order. Nothing is shared with any other frame, so a frame can be dropped or seeked to freely.

Layer III — mp3

Parameters up front, payload elsewhere

4 × granule×channel record4 × 59 bits

The slot holds bytes, not necessarily this frame's bytes. main_data_begin says how far back this frame's data actually starts — up to 511 bytes earlier, inside frames already gone past.

The structural difference

The bit reservoir is the one thing that makes a Layer III frame not a unit. A granule that needs more bits than its own frame provides reaches backwards into the unused tail of earlier frames. Layer II has no equivalent: each frame gets exactly its own bytes, so a demanding passage has to be quantized to fit. That single mechanism is why Layer III does more with the same bitrate — and why an mp3 file cannot be cut at an arbitrary frame boundary the way an mp2 file can.

03  /  per-frame parameters

How each layer says “decode it like this”

Layer II writes a variable-length run of fields whose size depends on the content. Layer III writes a block of fixed size whose contents then describe a variable-length payload.

Layer II

Subband count is not fixed: 27 normally, 30 above 96 kbit/s per channel (except at 48 kHz), 8 or 12 at low rates, and always 30 for MPEG-2. Allocation code widths shrink with frequency — 4 bits for subbands 0–10, 3 for 11–22, 2 for 23–29.

False friend

Both layers have a field called scfsi, and they mean different things. In Layer II it says which of the three scalefactors of one subband in this frame are actually transmitted (3, 2 or 1 values, covering parts 0–3, 4–7, 8–11). In Layer III it says which scalefactor bands granule 2 copies from granule 1. Same name, different axis: within-frame time in one, across-granule reuse in the other.

04  /  the payload

Fixed-width codes vs Huffman

This is where the two formats diverge completely, and it is the part mp2.cpp has to translate.

Layer II

Reading a sample

n = 2…16read n bits, value = code − (2^(n−1) − 1)
n = 17, 18, 19read 5, 7, 10 bits → 3 samples

The grouped case is a radix-3, radix-5 or radix-9 packing of three samples into one code, used where three levels of resolution would waste most of a bit each.

Layer III

Reading a value pair

pair code1–19 bits → (x, y), each 0…15
if x = 15+ linbits raw bits
if x ≠ 0+ 1 sign bit
then ysame again

32 table slots, of which 29 carry codes; the widest reaches magnitude 8206. Which table applies depends on which of the three regions the pair falls in.

05  /  scalefactors and stereo

Same words, different machinery

The one that catches people out

In Layer II joint stereo, above the bound the two channels share the samples and the allocation code — but scfsi and scalefactors are still read twice, once per channel. A parser that zeroes the second channel's allocation too early reads the wrong number of scalefactor bits and desynchronises for the rest of the frame.

06  /  why the conversion works

The numbers line up exactly

For all their differences, both layers sit on the same 32-band polyphase filterbank, and the frame sizes were chosen so that Layer III could subdivide what Layer II emits. That leaves an exact, one-to-one place for every Layer II sample.

1152 samples / channel / frame=2 granules × 576 lines
32 subbands × 36 samples=32 subbands × 18 lines × 2 granules
subband sb, parts 6g … 6g+5→granule g, lines 18·sb … 18·sb+17

Laying the samples out subband-major rather than in Layer II stream order is what makes the result behave like an mp3: the line index then tracks frequency, magnitudes fall away towards the top of the spectrum, subbands with no allocation become the trailing zero region, and per-region Huffman table selection has something real to select on.

Where it does not fit

Two edges. A Layer II sample of 15 or 16 bits exceeds the largest magnitude an mp3 value can hold (8206), so its top 1–2 bits go to the meta file and the rest stays in the mp3. And part2_3_length caps a granule at 4095 bits, which mono above roughly 300 kbit/s exceeds — there the converter splits a Layer II frame across 4, 6 or 12 granules instead of 2, at 3, 2 or 1 parts each.

Field widths, allocation tables, subband counts and scalefactor rules were read out of mp3_A.h, the minimp3-derived decoder this project is built on, rather than quoted from memory. Frame byte counts come from frame 0 of the test file. Companion to README.md in the same repository.
